# 기술 설계

## 목표 구조

서버가 전투 의미를 결정하고 클라이언트는 그것을 표현한다. 파티클을 보고 서버 상태를 역추론하는 구조는 지연과 치팅에 취약하므로 사용하지 않는다.

```text
Mob AI / Boss Phase
        ↓
SoulIntentProvider (server)
        ↓ compact snapshot when changed
SoulSignature network payload
        ↓
Client cache → particles / shader / sound / HUD
```

## 모듈 경계

- `soul`: `SoulIntent`, `SoulSignature`, 관찰 가능 여부와 동기화 규칙
- `sight`: 두 감지 능력, 집중 게이지, 쿨다운
- `combat`: 패링과 가드 결과, 보스 패턴 상태 머신
- `ash`: 수집, 저장, 사망 시 회수, 성장 해금
- `content`: 엔티티, 아이템, 블록, 구조물 등록
- `client`: 키 입력, 렌더링, 사운드, 접근성 설정

## 데이터 원칙

- 의도 변경 시에만 서버가 스냅샷을 보낸다. 매 틱 동기화하지 않는다.
- 강도·안정성은 `0..1`로 정규화하고 렌더러는 보간한다.
- 보스 패턴은 JSON 데이터로 옮길 수 있게 ID와 매개변수를 분리한다.
- 세이브 데이터에는 플레이어의 Ash, 해금 노드, 발견한 기억만 저장한다.

## 접근성

색각 차이를 고려해 모든 신호를 형태와 리듬으로 중복 표현한다. 화면 흔들림, 섬광 강도, 저주파 음향, 입자 밀도를 각각 조절할 수 있어야 한다. `생명을 비추는 빛`의 핵심 정보는 셰이더를 끈 상태에서도 읽을 수 있어야 한다.

## 테스트 전략

- 순수 자바 단위 테스트: 의도 전이, 집중 게이지, Ash 비용
- GameTest: 엔티티 의도 동기화, 사슬 파괴, 보스 페이즈 전환
- 수동 전투 시나리오: 60/120/200ms 지연, 낮은 입자 설정, 색각 프리셋
- 빌드 검증: 모든 커밋에서 Gradle `build`

## 첫 구현 순서

1. 개발용 명령으로 더미 몹의 `SoulIntent`를 바꾼다.
2. 셰이더 없이 파티클·사운드만으로 여섯 상태를 구분한다.
3. 집중 게이지와 키 입력을 붙인다.
4. 좀비 한 종에 세 개의 의미 있는 패턴을 매핑한다.
5. 플레이테스트 후에만 바로크 전용 엔티티를 만든다.
